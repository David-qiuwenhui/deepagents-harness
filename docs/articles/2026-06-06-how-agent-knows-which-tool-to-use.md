# Agent 怎么知道该用哪个工具？——从原理到实践

> 本文基于 deepagents-harness 项目，拆解 Agent 工具调用的核心机制。

## 一个问题

假设你的 Agent 有 10 个工具：查天气、算数学、搜网页、读文件、写文件、执行代码、发邮件、查数据库、翻译、生成图片。

用户说了一句："帮我算一下上个月的销售总额。"

Agent 怎么知道该调哪个？它不会写 `if-else`，那它是怎么做意图识别的？

答案只有四个字：**语义理解**。

## 工具在 LLM 眼里是什么？

在 Agent 架构中，工具不是"插件"，不是"路由表"，而是一份**结构化的函数说明书**。

以我们项目中的 `calculate` 工具为例：

```python
@tool
def calculate(expression: str) -> str:
    """计算数学表达式并返回结果。例如: '2 + 3 * 4'"""
    ...
```

当这个工具注册到 Agent 时，LangChain 会把它序列化成这样的 JSON 结构：

```json
{
  "type": "function",
  "function": {
    "name": "calculate",
    "description": "计算数学表达式并返回结果。例如: '2 + 3 * 4'",
    "parameters": {
      "type": "object",
      "properties": {
        "expression": {
          "type": "string",
          "description": "要计算的数学表达式"
        }
      },
      "required": ["expression"]
    }
  }
}
```

注意到了吗？这份 JSON 里只有三样东西：**名字、描述、参数格式**。没有逻辑，没有代码，只有"这个工具能做什么"的语义信息。

## 一次完整的工具调用流程

当用户发送消息时，整个流程是这样的：

```
用户: "帮我算一下 123 * 456"
         │
         ▼
┌─────────────────────────────────┐
│  发送给 LLM 的请求包含两部分：      │
│                                   │
│  1. messages（对话）              │
│     - system: "你是一个有用的助手" │
│     - user: "帮我算一下 123*456"  │
│                                   │
│  2. tools（工具清单）              │
│     - get_current_time: 获取时间  │
│     - calculate: 计算数学表达式    │
│                                   │
│  LLM 阅读 tools，理解每个工具的     │
│  能力，结合用户问题做语义匹配       │
└─────────────────────────────────┘
         │
         ▼ LLM 的决策
┌─────────────────────────────────┐
│  LLM 返回 tool_call：             │
│                                   │
│  {                                │
│    "name": "calculate",           │
│    "arguments": {                 │
│      "expression": "123 * 456"    │
│    }                              │
│  }                                │
│                                   │
│  注意：LLM 不仅选了工具，           │
│  还自己填充了参数值！               │
└─────────────────────────────────┘
         │
         ▼ 框架执行
┌─────────────────────────────────┐
│  LangGraph 框架：                 │
│  1. 解析 tool_call               │
│  2. 调用 calculate("123 * 456")  │
│  3. 得到结果："123 * 456 = 56088" │
│  4. 把结果作为工具消息回传给 LLM   │
└─────────────────────────────────┘
         │
         ▼ LLM 生成最终回复
┌─────────────────────────────────┐
│  LLM 拿到工具结果后：             │
│                                   │
│  messages: [                      │
│    ...,                           │
│    { role: "assistant",           │
│      tool_calls: [...] },         │
│    { role: "tool",                │
│      content: "123*456 = 56088" } │
│  ]                                │
│                                   │
│  LLM 基于这个上下文生成回复：      │
│  "123 乘以 456 等于 56088。"      │
└─────────────────────────────────┘
```

这就是 ReAct（Reasoning + Acting）模式的一次完整循环：**推理 → 行动 → 观察**。

## LLM 是怎么做"意图识别"的？

关键洞察：**LLM 不是在做分类，而是在做阅读理解。**

想象你是一个人类助手，面前摆着一份工具手册，每条记录写着：

- **get_current_time**：获取当前日期和时间
- **calculate**：计算数学表达式并返回结果
- **search_web**：搜索互联网获取最新信息
- **read_file**：读取本地文件内容

当用户问"现在几点了"，你会怎么选？你会读这些描述，发现 get_current_time 的"获取当前日期和时间"正好匹配——这就是 LLM 在做的事。

它不是在做 `if "几点" in message` 这样的关键词匹配，而是在理解：
1. **用户想要什么** —— 获取当前时间信息
2. **哪个工具能满足** —— get_current_time 的能力描述匹配这个需求
3. **需要传什么参数** —— get_current_time 不需要参数

这套能力的底层是 LLM 的 **Function Calling**（函数调用）特性。现代 LLM（GPT-4、GLM-5.1、Claude 等）都专门训练过这个能力——在理解文本的同时，生成结构化的函数调用 JSON。

## Docstring 为什么这么重要？

因为 docstring 就是工具的"简历"。LLM 纯靠阅读它来决策。

看两个对比：

**模糊的描述（不好）：**
```python
@tool
def tool_a(query: str) -> str:
    """处理输入"""
    ...
```

**精确的描述（好）：**
```python
@tool
def search_product(query: str) -> str:
    """在商品数据库中搜索匹配的商品。支持按名称、品牌、类别搜索。
    query: 搜索关键词，例如 'iPhone 15' 或 '耐克运动鞋'"""
    ...
```

写好 docstring 的几个原则：

1. **说清楚工具做什么** —— 不是"处理数据"，而是"在商品数据库中搜索"
2. **给出使用示例** —— 帮助 LLM 理解参数的格式
3. **说明边界和限制** —— "仅支持中文搜索"比让 LLM 自己试错好
4. **工具之间要互不重叠** —— 如果你有 `search_web` 和 `search_knowledge_base`，描述里要明确区分适用场景

## 10 个工具不会选错吗？

现实情况是：**会选错，但概率可控。**

影响选择准确率的因素：

| 因素 | 影响 | 建议 |
|------|------|------|
| 工具数量 | 超过 20 个时准确率下降 | 按场景分组，动态注入相关工具 |
| 描述质量 | 模糊描述导致误选 | 写精确、有边界的描述 |
| 描述重叠 | 两个工具描述相似时 LLM 会混淆 | 明确区分适用场景 |
| LLM 能力 | 更强的模型选择更准 | 复杂场景用更强的模型 |

实际项目中，5-10 个工具用得好描述基本不会有问题。超过 20 个时可以考虑**工具路由**——先用一个轻量 LLM 判断需要哪类工具，再只注入相关工具给主 LLM。

## 在我们的项目中怎么加新工具？

只需要两步：

**第一步**：在 `src/agent/tools.py` 中定义工具：

```python
@tool
def search_web(query: str) -> str:
    """在互联网上搜索信息，返回相关结果。适用于需要最新资讯、事实查询的场景。"""
    # 调用搜索 API...
    return results
```

**第二步**：在 `src/agent/server.py` 中注册：

```python
from agent.tools import calculate, get_current_time, search_web

TOOLS = [get_current_time, calculate, search_web]
```

就这样。框架会自动把新工具序列化、发给 LLM、处理调用流程。LLM 会在需要时自主选择使用它。

## 总结

| 概念 | 解释 |
|------|------|
| 工具的本质 | 一份结构化的函数说明书（name + description + parameters） |
| LLM 怎么选工具 | 语义理解——阅读工具描述，匹配用户意图 |
| 不是什么 | 不是关键词匹配，不是 if-else 路由，不是规则引擎 |
| 核心能力 | LLM 的 Function Calling 特性（专门训练过的） |
| 描述的重要性 | docstring = 工具简历，写得好坏直接决定选择准确率 |

Agent 的工具调用，本质上是把"决策权"交给了 LLM。框架只负责执行，不负责选择。这就是 Agent 和传统软件最大的区别——**行为不是程序员写死的，而是 LLM 根据上下文动态决定的**。
